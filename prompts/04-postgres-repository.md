## Goal

Persist a whole validated configuration document in Postgres with tenant scope and a conditional revision update. Tests run against a real database.

## Schema

Create `db/migrations/001_configurations.sql`:

```sql
CREATE TABLE configurations (
  tenant_id text NOT NULL,
  id text NOT NULL,
  schema_version integer NOT NULL CHECK (schema_version > 0),
  revision integer NOT NULL CHECK (revision > 0),
  data jsonb NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, id),
  CONSTRAINT configurations_data_object CHECK (jsonb_typeof(data) = 'object')
);
```

This is the table. Do not add a `position` column. Do not add JSONB indexes. Application code still validates the full block schema before calling the repository; the database constraints are a backstop, not the only validation.

`updated_at` is assigned by Postgres `now()` on insert and update. Callers cannot pass a timestamp into the write functions.

## Repository

Place it in `apps/config-service/src/configurations/`. It receives a `pg` pool and does not know about HTTP or React.

Operations:

- `insertConfiguration({ tenantId, id, document })` inserts `schema_version` from the document, `revision` 1, and `data`. The id is generated by the service layer in a later prompt; this function receives it. Fail with a typed unique-violation result if the same tenant and id already exist. Do not upsert.
- `getConfiguration({ tenantId, id })` returns the row or a not-found result. The `WHERE` clause includes both `tenant_id` and `id`.
- `updateConfiguration({ tenantId, id, expectedRevision, document })` runs one conditional update:

```sql
UPDATE configurations
SET data = $1::jsonb,
    schema_version = $2,
    revision = revision + 1,
    updated_at = now()
WHERE tenant_id = $3
  AND id = $4
  AND revision = $5
RETURNING id, schema_version, revision, updated_at, data;
```

All parameters are bound. If no row returns, run a second `SELECT` that is also filtered by `tenant_id` and `id`. If that select finds nothing, return not-found. If it finds a row, return revision-conflict. Do not query by id without `tenant_id` to see whether another tenant owns it.

Map a returned row to the `Configuration` contract: `updatedAt` from `updated_at` as ISO-8601 UTC, `schemaVersion` from `schema_version`, `data` as the JSON object. Re-parse the row with the contract schema before returning it. A row that fails the schema is an internal error, not a successful read.

## Tests

Against `reactiv_test`:

- insert then get returns the same sections, order, and colors, revision 1, and a timestamp
- get for another tenant returns not-found for the same id
- two updates with the same `expectedRevision` — run the second after the first has committed — the second returns revision-conflict and the stored revision is 2, not 3
- a concurrent pair is required: start two updates that both read revision 1, and assert exactly one succeeds. Use two connections and a short delay or a transaction that holds the row only for the duration of the single `UPDATE`. The single conditional `UPDATE` is the concurrency control; do not add a locked read that hides a lost-update bug
- an unknown id returns not-found and does not insert
- `updated_at` changes on a successful update and is database-assigned
- a failed conditional update leaves `data` and `updated_at` unchanged. Compare the whole JSON and the timestamp

Clean up rows created by tests. Do not share rows with a future seed.
